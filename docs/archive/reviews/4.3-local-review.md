# Convolver correctness review and modernization options

Reviewed 17 October 2026.

The overlap-save and uniform partition scheduling are mathematically sound. The implementation nevertheless contains reproducible defects in partition loading, delayed input history, memory copying, complex arithmetic and sample conversion. Small fixes and regression tests are included locally. The original Windows applications have not been rebuilt or validated in a host; the remaining host defects below still prevent calling this a release-ready revival.

The most consequential historical finding is that Album Player reused the engine and already has Linux and Windows x64 derivatives. Separately, Convolver's configuration format became an interface used by other products. Recovering the derivative source and preserving configuration compatibility should precede a new port.

## Convolution correctness

Let `B` be the processing hop and `N = 2B` the FFT length. Each impulse-response partition contains at most `B` consecutive taps, padded to `N`. Each input transform covers the preceding and current `B` samples. At step `m`, the active accumulator is:

`Y_m = sum_p H_p * X_(m-p)`

The circular accumulator correctly schedules each product into the corresponding future block, clears a consumed slot before reuse, applies the inverse transform, and retains the second half. Scaling the filter spectra by `1/N` compensates for FFTW's unnormalised inverse. The frame-transfer order adds `B` samples of processing latency. Plain overlap-save is the single-partition case. That structure does not need replacing to obtain correct convolution.

The important condition is that the IR split stride and processing hop are identical. The original code violated it for FFT sizes requiring padding.

### Fixed defects

| Priority | Defect and observable effect | Local correction |
|---|---|---|
| High | **IR partitions move in time.** A 34-tap IR with two partitions is split at 17 taps, but the runtime hop is rounded to 18. Tap 17 is therefore rendered as tap 18. With three 17-tap chunks, the last chunk shifts by two samples. Common power-of-two configurations can conceal this. | Split the IR using the rounded hop from the outset. filter.cpp (`source/convolver/convolution/filter.cpp:140`; original local snapshot) |
| High | **Positive input delays overwrite FFT history.** Future samples are written into the same circular storage containing the previous overlap. For `B=4`, input impulse at frame 3, IR impulse at tap 3 and input delay 2, the original ring model emits at frame 4 instead of frame 12, including processing latency. | Keep pending delayed input in separate storage and commit only the current frame to FFT history; clear both on reset. convolution.cpp (`source/convolver/convolution/convolution.cpp:128`; original local snapshot) |
| High | **An ordinary unity-gain path reads beyond its allocation.** `FastArray` copies the destination byte count when assigning an `N`-sample input to an `N+2`-sample FFT buffer. AddressSanitizer reproduces the eight-byte overread. | Copy the source byte count and zero the extra destination elements. samplebuffer.h (`source/convolver/convolution/samplebuffer.h:287`; original local snapshot) |
| High | **Packed PCM sign decoding is wrong.** Negative 24-bit samples are assembled as positive integers; missing switch breaks also break 20-bit decoding and assert in debug builds. | Decode valid bits and explicitly extend the sign. sample.h (`source/convolver/convolution/sample.h`; original local snapshot) |
| High | **Narrow PCM is misaligned inside larger containers.** 16/20-bit output in 24-bit containers and 16/20/24-bit input/output in 32-bit containers are handled without the required left alignment. This causes substantial gain errors and invalid padding bits. | Decode/store valid bits in their correct positions using unsigned byte operations, including unaligned-buffer tests. sample.h (`source/convolver/convolution/sample.h`; original local snapshot) |
| High | **VST shared buffers destroy input.** Outputs were written before inputs were read, although a host can reuse input buffers for output. The same code ignored the supplied additive converter and used the internal float size for double buffer accounting. | Capture all input channels before any output; use the supplied conversion methods; treat null input channels as silence. sample.h (`source/convolver/convolution/sample.h:204`; original local snapshot) |
| High | **Different routing fan-outs break gain calculation.** The loop bounds every path by the first path's output count. Fewer outputs cause an out-of-bounds read; more outputs are omitted from attenuation calculations. | Use each path's own output count. channelpaths.cpp (`source/convolver/convolution/channelpaths.cpp:409`; original local snapshot) |
| Medium | **The three-multiply complex identity loses small cross terms.** In float arithmetic, `(10000 + 0.0001i)^2` produces imaginary part zero instead of approximately two. This is avoidable cancellation, not a scheduling failure. | Use the direct real and imaginary products in both FFTW multiplication kernels. convolution.cpp (`source/convolver/convolution/convolution.cpp:566`; original local snapshot) |
| Medium | **An empty IR is not rejected.** The code constructs an exception without throwing it and subsequently takes a remainder with a zero divisor. | Throw before constructing transform state. filter.cpp (`source/convolver/convolution/filter.cpp:129`; original local snapshot) |

The delay correction costs one additional `N`-float buffer per input channel plus one copy per input sample. The numerical correction uses another multiplication per complex product. Neither change has been benchmarked with real FFTW or in an audio host. Correctness should be established before recovering any performance through a different buffer layout or SIMD implementation.

### Verification boundaries

The portable harness compiles the **actual source bodies** for filter loading, buffer assignment, convolution scheduling, mixing and complex multiplication. It replaces Windows plumbing, file reading and FFTW with small test adapters. The transform adapter computes an unnormalised DFT with FFTW-compatible real/complex layout; the expected output is independently calculated by direct, double-precision linear convolution.

The core suite covers single and multiple partitions; short, odd, non-power-of-two and partially filled filters; irregular callback sizes; positive/negative routing weights; multiple inputs and outputs; unused output channels; delays through the permitted small-block boundary; unity-gain fast paths; empty IR rejection; and reset followed by silence. The principal matrix uses IR lengths from 1 to 127 taps and partition counts 1, 2, 3, 4 and 8. These are algorithm and boundary tests, not long-filter stress tests.

The host harness compiles actual conversion and VST transfer code, including shared buffers, additive processing, null channels and float/double interfaces. It includes the actual no-dither/no-noise-shaping scaling but substitutes a checked integer-floor operation for the Boost boundary. Gain tests compile the original accumulation statements with unequal routing counts. AddressSanitizer and UndefinedBehaviorSanitizer are enabled. The saved original archive reproduces the defects, and ordinary unpadded/no-delay cases serve as passing controls.

The corrected sources pass **444 core checks, 36 conversion/transfer cases and two gain cases**. The worst absolute error in the small-filter core matrix is **4.8494 × 10⁻⁸**, against a threshold of 3 × 10⁻⁵. That figure measures these test inputs and the DFT adapter, not real FFTW error for long production filters. The original host code passes four control cases and fails the other 32.

Run from this directory:

```sh
python3 tests/run_all.py
python3 tests/run_all.py --baseline
```

The baseline command succeeds when its expected failures are reproduced and its control passes. Detailed outputs are saved in verification-results.json (`review/verification-results.json`; original local snapshot) and baseline-results.json (`review/baseline-results.json`; original local snapshot).

This does **not** validate real FFTW planning, alignment requirements or threading; libsndfile behaviour; the configuration parser end to end; historical Ooura/Intel alternative branches; the complete dithering/noise-shaping system; native Windows builds; or audio-host operation. The adapter makes a few explicitly listed syntax repairs for old MSVC template parsing without modifying that unrelated production code. Full-length numerical tests and native CI remain necessary before release.

## Further defects and release work

These findings are source-level review findings unless otherwise stated; they are not included in the tested core patch.

1. **Offline processing loses final audio.** convolverCMD.cpp (`source/convolver/convolverCMD/convolverCMD.cpp:246`; original local snapshot) stops at input EOF and pads only the remainder of a short final read. An input exactly divisible by the chosen buffer length receives no drain frames. Even an identity filter loses the final latency-length segment. Introduce an explicit drain operation, retain the true IR length, and specify whether an offline render trims initial latency and includes the full `input_length + IR_length - 1` tail, adjusted for routing delays. Test an impulse in the final input frame for both exact and partial buffer lengths.

2. **The VST UI can stop audio processing.** SelectFilter (`source/convolver/convolverVST/convolverVST.cpp:363`; original local snapshot) holds the same mutex as the audio callback across the file dialog and filter/FFT construction. Build a replacement state outside the audio lock and publish it at a safe processing boundary. A revival also needs explicit behaviour when no filter is loaded or processing has been aborted: the present callback can return without filling replacing outputs.

3. **Tail reporting and draining are incomplete.** VST getGetTailSize (`source/convolver/convolverVST/convolverVST.cpp:453`; original local snapshot) returns a half-partition length, which describes processing latency rather than an arbitrary FIR's tail. The DMO Discontinuity (`source/convolver/convolverWMP/convolver.cpp:1012`; original local snapshot) and input-ownership handling do not implement an explicit FIR tail drain. Validate end-of-stream, seeks and resets in a real host.

4. **Conditional DMO bypass sizing is unsafe.** The wrapper computes input consumption from the negotiated input/output frame sizes, but disabled processing copies the input byte count unchanged. A client using different input/output channel counts or sample widths can therefore exceed output capacity. WMP's own disabled-filter flow skips processing according to the code comment, so this is especially relevant to other DMO clients. Native format-negotiation tests are required before choosing bypass semantics.

5. **Full-width 32-bit PCM has a positive-endpoint risk.** The unchanged `ConvertSample_pcm32<T,32>` specialization calculates `2^31 - 0.5` in `float`, which rounds to `2147483648`. Positive full-scale output then reaches an integer conversion above `INT32_MAX`. The native Boost conversion's exact failure behaviour has not been tested. This case needs explicit endpoint saturation and tests of the real conversion implementation; it is separate from the corrected narrow-container formats.

6. **Modern compiler and input-validation work remains.** Windows/ATL types are embedded in the DSP headers; the custom array has unused methods with invalid standard C++ syntax; dormant backend paths have stale code. Bound frame/channel counts before narrowing, validate finite gains and delays, check FFT plan creation, and test malformed configs and filter lists. Existing platform assumptions are reasons to isolate the core, not evidence that a mechanical compiler upgrade is sufficient.

## Projects that reused Convolver

### Album Player reused the engine

The official [Album Player Linux manual](https://albumplayer.ru/linux/album_player_linux_manual_ru.pdf) credits ConvolverVST and describes it as the prototype for its convolver. Binary inspection adds stronger evidence:

- The [Windows x64 package](https://albumplayer.ru/ap2convolver_x64.zip) contains a native AMD64 `convolverVST.dll` identifying itself as “ConvolverVST for Album Player”. It retains distinctive `ChannelPaths`, `FastArray<float>` and ConvolverVST class names.
- The [Linux x64 package](https://albumplayer.ru/linux/aplayer64.tar.gz) retains `Convolution::calculateOptimumAttenuation`, `Convolution::mix_input`, `Convolution::mix_output` and matching `ChannelPaths` methods, including their distinctive signatures.
- Album Player's developer described adapting the original plug-in's settings handling in a [July 2023 forum reply](https://hi-fi-forum.net/forum/printthread.php?page=124&tid=142398). Its [Linux download page](https://albumplayer.ru/linux/english.html) currently offers version 2.19 and is dated 17 September 2026.

This establishes derivative lineage, not that the old bugs survive in those binaries. Neither derivative was executed or subjected to the DSP tests. Package/member hashes and matching strings are in downstream-evidence.json (`review/downstream-evidence.json`; original local snapshot).

The sampled packages did not contain modified source or a separate licence document, and the inspected landing pages did not expose a source download. That leaves a practical source-recovery question, not a legal conclusion. Obtaining and comparing the adaptation would reveal which portability, build and host changes already exist. No contact has been made on your behalf.

Preserve old configuration semantics deliberately, including the unusual channel/weight syntax and zero-as-unity convention. A cleaner future format should be versioned and accompanied by an importer and compatibility fixtures. Existing consumers should not inherit silently changed routing behaviour.

## Modernization choices

| Direction | Useful outcome | Relative commitment and tradeoff |
|---|---|---|
| Preserve and repair | A source repository with release provenance, documented fixes, regression vectors and an authoritative configuration specification. | Lowest continuing commitment; immediately useful to users and derivative maintainers. |
| Recover Album Player changes and extract a portable core | A small C++ library plus CLI with native Windows/Linux/macOS builds, deterministic rendering and exact configuration compatibility. | Moderate commitment. Existing derivative work may avoid repeating a Linux/x64 port; source availability is unresolved. |
| Release a modern multichannel plug-in | VST3 first, with CLAP/AU/LV2 according to actual host demand, preset/state storage, clear routing and current architecture support. | Higher commitment: host lifecycle, latency, tail, bus negotiation and safe filter changes are as important as the convolution loop. |
| Contribute interoperability to established projects | Compatibility fixtures, configuration validation/conversion, reference renders, and fixes shared with relevant maintainers. | Potentially the greatest user benefit per maintenance hour. CamillaGUI already has an importer, so improve and test it before writing another. |
| Build a complete system DSP application | Room correction/crossover processing with device selection, resampling, clock handling, routing UI and packaging. | Highest commitment and substantial overlap with existing products. Select a concrete unmet need first. |

[CamillaDSP](https://github.com/HEnquist/camilladsp) already provides a cross-platform FIR/IIR, mixing and delay engine. [Hang Loose Convolver](https://accuratesound.ca/hlc-plugin/) already provides cross-platform plug-in/standalone convolution with multichannel configuration support and filter switching. A revived Convolver needs a specific reason to choose it, such as a small transparent library, exact legacy compatibility, an excellent routing interface, or reproducible numerical guarantees. The historical Pentium benchmarks do not establish a present speed advantage.

For a portable core, separate configuration parsing, IR loading, processing state and host adapters. Use RAII for buffers and FFT plans; remove Windows types from the processing API; select a maintained FFT backend and libsndfile version; add CMake and native CI. Make the contract explicit: prepare, process arbitrary frame counts, reset, drain, latency and tail. Preserve a scalar/direct reference for numerical tests.

For real-time operation, allocate and plan outside callbacks, use a defined state-swap strategy, and test filter/sample-rate changes. Choose block size from a latency target rather than exposing partition count alone. Uniform partitioning is a good first validated baseline; non-uniform partitions or a direct-convolution head are later options when measurements show a latency/CPU benefit. Benchmark worst callback time, channel count, IR length and memory on x64 and ARM64. Do not add GPU processing or force all arithmetic to double without an application-specific benefit.

The current [VST3 SDK is MIT licensed](https://github.com/steinbergmedia/vst3sdk#license--usage-guidelines); [CLAP is also MIT licensed](https://github.com/free-audio/clap). The source headers here say GPL version 2 or later. Framework/dependency licences remain separate decisions: for example, [current JUCE is AGPLv3/commercial](https://github.com/juce-framework/JUCE/blob/master/LICENSE.md). Retain the historical notices and check the exact chosen dependency versions before distribution or any licensing change.

My recommended order is to preserve this baseline and its tests, recover Album Player's modified source if available, and produce a portable core plus a trustworthy offline renderer. Then choose between a modern plug-in and contributing interoperability work to existing software. That sequence produces useful results even if a full product revival proves unnecessary.
