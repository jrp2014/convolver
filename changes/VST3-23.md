# VST3-23

## Fixed

- VST3 (VST3-23, jrp's review of PR #279): choosing a preset in the
  plug-in's window, then changing Latency before the window had caught up,
  no longer puts the window back at the preset's Latency. The plug-in
  played and saved the 256 the user chose, while the window showed the
  preset's 2048 and reported 2048 to the host as an edit. Choosing 256 again
  while the window still showed 256 played and saved 2048. The latest choice
  now wins everywhere. See the
  [adapter contract](../docs/develop/plugin-contract.md).
- VST3 (VST3-24, jrp's review of PR #279): a filter chosen in the window
  just before the host restored a preset no longer replaces that preset
  when the host delivers the window's request late. The project saved the
  older window choice (in jrp's test, a different impulse and Latency
  2048 instead of the preset's 512), so reopening it recalled different
  processing. The restored preset now keeps playing and is saved, and the
  Convolver log says why the window's choice was not loaded. If the later
  host preset is refused, the window's choice plays, the window shows its
  settings, a Gain or Mix set after the choice keeps its value, and the
  host is told the project changed.
- VST3 (VST3-24): a host preset the plug-in refuses, such as one made for
  another sample rate, no longer leaves its Bypass shown in the host while
  the plug-in keeps playing with its own.

## For contributors

- Tests (VST3-23, VST3-24): `vst3.adapter` `latest_action_wins` is a table
  of short sequences of user and host actions (window presets, a filter
  without settings, Latency, Gain mode, Gain, Mix, Bypass, accepted and
  refused host presets), each with the filter, Latency, Gain mode, Gain,
  Mix and Bypass that should win. Gain, Mix and Bypass reach the processor
  in the host's next block: the window shows each at once, a save before
  that block keeps what plays, and after it all three must agree. Each runs
  with every choice of delivery between the actions (none, the processor's
  queue only, both ways), in three restore orders (the processor first, the
  controller first, and the processor, then delivery, then the controller),
  for a host with `setDirty` and one without it that hands every edit back,
  through connections that deliver later. It checks the window, what plays,
  what `getState` saves, the last Latency edit and latency read the host had
  since the last action, and that the host was told the project changed
  when a window choice wins, so a sequence in which every component agrees
  on the wrong value fails. Named rows keep jrp's cases from his review of
  PR #279, his rerun and his review of this PR at 4cf4712b, and the
  independent review's at 574686d.
  `window_choice_orders` checks what the window is told of refused and
  accepted choices and a Gain set after choosing a window preset;
  `refused_state_accepted_later` restores a refused preset again once it
  suits the host.
- VST3 controller (VST3-23, VST3-24): one count numbers every action the
  controller takes or hears (Latency, Gain mode and load requests, each
  `setComponentState`, each Gain or Mix set), replacing VST3-18's bits for
  Gain and Mix and its request numbers kept at each restore. The processor's
  `RestoreFollow` keeps the restores whose report request has not arrived,
  oldest first. The first version of this PR also re-sent a superseded
  choice for hosts that restore the processor alone; jrp's review found it
  let a host that delivers messages between its two restore calls replace
  the restore, so it was removed: the SDK has hosts restore both halves.
